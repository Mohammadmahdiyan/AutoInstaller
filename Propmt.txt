Fix the GTA San Andreas Mod Manager startup wizard by addressing BOTH navigation/logic bugs and the UI/design issues described below.

IMPORTANT:
- Treat this as a bug-fix and UI-refinement task.
- Inspect the existing wizard/navigation/cache/folder-picker implementation before changing it.
- Preserve all existing functionality that is not directly related to these issues.
- Do not rewrite the entire application unnecessarily.
- Do not introduce duplicate state or duplicate cache systems.
- Keep the existing project architecture and framework.
- The final result must behave like a professional Windows Setup/Installer wizard, not a raw HTML form.

# PART 1 — Wizard Navigation / Step 1 / Step 2 / Step 3

## 1.1 Correct Previous / Next button behavior

There is currently a navigation bug:

When the user is on:

Step 3

and clicks:

Previous

the wizard correctly goes to:

Step 2

But when the user clicks Previous again:

Step 2 → Step 1

the Next button disappears.

This is WRONG.

The navigation buttons must always reflect the current step.

Required behavior:

### Step 1
- Previous: HIDDEN or DISABLED according to the existing wizard design.
- Next: VISIBLE and ENABLED when Step 1 requirements are satisfied.

### Step 2
- Previous: VISIBLE and ENABLED.
- Next: VISIBLE and ENABLED because Step 2 is OPTIONAL.
- The user must be able to continue from Step 2 even when its input is empty.

### Step 3
- Previous: VISIBLE and ENABLED.
- Next: Keep the existing behavior appropriate for the final/current step.

Most importantly:

Step 3
→ Previous
→ Step 2
→ Previous
→ Step 1

must result in Step 1 having its normal Next button available.

Do NOT permanently hide/remove the Next button when navigating backward.

The button visibility/state must be recalculated whenever the active step changes.

Do not rely on one-time initialization such as:
- hiding Next during startup
- showing it only once
- changing its state without restoring it when returning to Step 1

Instead, navigation controls must be derived from the CURRENT active step.

## 1.2 Step 1 requirements

Step 1 selects the main GTA San Andreas Game Folder.

- Load the cached Game Folder on startup.
- If the cached path is valid, display it in Step 1.
- Do not ask the user to select it again unnecessarily.
- Step 1 must retain its cached value when navigating backward from later steps.

## 1.3 Step 2 requirements

Step 2 selects the Base GTA SA Mods Address.

Examples:

H:\F\Mods
G:\F\Mods
F:\File\Game\AddonsSa

Step 2 is OPTIONAL.

Therefore:

- Empty Step 2 input is valid.
- The Next button must NOT be disabled merely because Step 2 is empty.
- An empty Step 2 value must not invalidate the wizard.
- A selected Step 2 path must be saved to Cache.
- The cached Step 2 path must be restored when the application starts.
- The cached Step 2 path must also be restored when navigating backward from Step 3.

## 1.4 Critical Cache preservation rule

Do not overwrite valid cached values with temporary empty UI state.

Example:

Cache:
H:\F\Mods

User:
Step 3 → Previous → Step 2

The Step 2 input must still contain:

H:\F\Mods

If the UI temporarily initializes with an empty string during rendering/navigation, that empty string MUST NOT overwrite the Cache.

Only an explicit user change/selection should update the stored value.

Apply the same rule to Step 1 Game Folder.

# PART 2 — FIX STEP 2 → STEP 3 FOLDER PICKER PATH BUG

There is currently another bug.

Example:

The user selects this Base Address in Step 2:

H:\F\Mods

When the user reaches Step 3 and opens the Mod Folder Picker, it currently opens at:

H:\F\

This is WRONG.

It must open at EXACTLY:

H:\F\Mods

The Step 2 Base Address must be passed to the Step 3 Folder Picker without accidentally removing the final directory component.

## Required behavior

If Step 2 contains:

H:\F\Mods

then Step 3 Folder Picker initial directory must be:

H:\F\Mods

NOT:

H:\F\

NOT:

H:\F

NOT:

H:\F\Mods\

unless the folder-picker API internally normalizes the trailing slash.

If Step 2 contains:

G:\F\Mods

then open at:

G:\F\Mods

If Step 2 contains:

F:\File\Game\AddonsSa

then open at:

F:\File\Game\AddonsSa

## Important implementation requirement

Inspect the code that converts the Step 2 value into the Step 3 Folder Picker initial path.

Look specifically for bugs involving:

- path.dirname()
- parent directory calculation
- path parsing
- removing the last path segment
- trailing slash handling
- resolving the selected directory as if it were a file
- converting a folder path to its parent
- incorrect use of path.basename()
- incorrect use of path.resolve()
- URI/file URL conversion
- Windows path separator handling

The Step 2 value represents a DIRECTORY.

It must be treated as a directory, not as a file.

Do not calculate its parent directory before opening the picker.

## Folder Picker behavior

The Base Address is ONLY the initial directory.

For example:

Step 2:

H:\F\Mods

Step 3 Folder Picker opens at:

H:\F\Mods

The user can then navigate/select:

H:\F\Mods\Maps
H:\F\Mods\Maps\object gta v
H:\F\Mods\Vehicles
etc.

Do NOT force the selected mod folder to equal the Base Address.

If Step 2 is empty:

- Use the normal existing operating-system Folder Picker behavior.
- Do not construct a path from an empty string.
- Do not accidentally use the parent directory of another path.

# PART 4 — DESIGN / UI FIXES

## 4.1 Title and Subtitle layout

For every wizard step that contains:

Title
Subtitle
Input
Browse

the elements must have clearly separated vertical layout.

Correct structure:

Title

Subtitle

[ Input................................ ] [ Browse ]

Title and Subtitle MUST NEVER overlap the Input.

Do not use absolute positioning or incorrect fixed heights that cause the text to render over the input.

The layout must remain correct at different window sizes.

Recommended structure:

Step container
 ├── Title
 ├── Subtitle
 └── Input row
      ├── Input
      └── Browse button

Use proper spacing, margins, padding, and layout containers.

The Title and Subtitle should be visually associated with the step but completely outside the Input row.

## 4.2 Input + Browse professional setup appearance

The path Input and Browse button currently look too much like raw HTML controls.

Redesign them to resemble a professional Windows Setup.exe / Windows Installer control.

Requirements:

- Modern
- Clean
- Professional
- Windows Installer-like
- Appropriate internal padding
- Subtle border
- Proper control height
- Clear focus state
- Hover state
- Pressed state
- Disabled state
- Slightly rounded corners if consistent with the existing application UI
- Proper spacing between Input and Browse
- Good typography
- Good alignment
- Visually balanced proportions

The result should NOT look like:

<input>
<button>

from an unstyled HTML page.

Instead, it should look like a polished desktop installer wizard.

## 4.3 Path input behavior

The path input should visually communicate that it is a filesystem/path selector.

Requirements:

- Text should be vertically centered.
- Long paths should remain usable.
- Input should have enough horizontal space.
- Browse button should have a consistent width/height.
- Input and Browse button should align perfectly on the same row.
- Focus should be clearly visible.
- Disabled state should be visually distinct.
- Avoid excessive rounding if it conflicts with the existing Windows-style UI.

## 4.4 Preserve existing visual identity

Do NOT replace the entire application's existing theme.

The new controls must integrate with the current application:

- Existing colors
- Existing typography
- Existing dark/light theme
- Existing spacing system
- Existing wizard layout

Only improve the problematic areas.
